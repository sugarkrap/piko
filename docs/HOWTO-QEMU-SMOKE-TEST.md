# How to smoke-test a kernel build under QEMU

Boots a freshly built `zImage` before it ever touches the last spare board.
CI runs the scripted version of this (`flash/qemu-smoke-test.sh`) on every
full update package; this doc is the manual path and the traps behind it.

**What this does and does not prove.** QEMU never modelled Corgi — only
Spitz (PXA270), and that machine was removed in QEMU 9.2. So `-M spitz`
exercises the *shared* PXA2xx / `sharpsl_pm` boot path only. It has no W100
chip and never sets `machine_is_corgi()`, so `corgi.c` / `corgi_pm.c` /
`w100fb.c` never execute here. A green smoke test means "the shared boot
path is not broken"; it is necessary, not sufficient.

## The QEMU binary

Build **9.1.0** from source — the last release with the `spitz` machine.
Two build-time issues, both the same "old software vs. very new host
tooling" pattern:

- **`mkvenv`'s bootstrap needs Python's `distlib`.** Rather than installing
  it system-wide, use a local venv:

  ```sh
  python3 -m venv pyvenv-bootstrap
  pyvenv-bootstrap/bin/pip install distlib
  ./configure --python="$PWD/pyvenv-bootstrap/bin/python3" --disable-libnfs
  ```

- **`block/nfs.c` fails against modern `libnfs`** (`nfs_pread_async` /
  `nfs_pwrite_async` signatures changed upstream since QEMU 9.1). Nothing
  here needs an NFS disk backend, so `--disable-libnfs` sidesteps it
  rather than patching dead code.

## Two traps that look like kernel bugs but are not

1. **`-M spitz` needs `CONFIG_MACH_SPITZ=y` compiled in**, separate from
   whatever machine the real board needs. A kernel built without it hangs
   in `dump_machine_table()` with **zero console output at all** — no
   panic, no banner, nothing. Check this first before chasing a regression.
   Multiple machine descriptors coexist fine in one image; QEMU's board ID
   (713) and the real device's are matched independently at runtime.

2. **`CONFIG_CMDLINE_FORCE=y` silently discards `-append`.** It is required
   on real hardware (forces `console=tty0`, which is the only console this
   device has — there is no serial cable), but it means QEMU never sees
   `console=ttyS0` and you get a silent boot. Temporarily flip the config:

   ```sh
   ./scripts/config --enable MACH_SPITZ \
       --set-str CMDLINE "console=ttyS0 earlyprintk" \
       --disable CMDLINE_FORCE
   make ARCH=arm CROSS_COMPILE=... olddefconfig
   make ARCH=arm CROSS_COMPILE=... -j"$(nproc)" zImage
   ```

   **Restore `console=tty0` + `CMDLINE_FORCE=y` and rebuild before flashing
   anything to the device.** Never ship the QEMU-testing config variant.

## Running it

```sh
qemu-spitz/build/qemu-system-arm -M spitz \
    -kernel path/to/zImage \
    -initrd path/to/initramfs.cpio.gz \
    -append "console=ttyS0 earlyprintk" \
    -serial stdio -nographic -monitor none
```

A working boot prints `Machine: SHARP Husky` (or `Spitz`, depending on the
config variant) within the first ~10 lines, then normal init through to a
shell prompt if an initramfs is attached. `spitz_misc_charging: Charging
on.` confirms `sharpsl_pm`'s runtime path actually executes rather than
merely compiling.

Total silence almost always means trap 1 above, not a real kernel bug.

Build the throwaway initramfs with `tools/build-initramfs.sh`. Note that
applet symlinks have to be generated by listing `busybox --list` through
`qemu-arm` user-mode emulation, since the ARM binary cannot run directly on
an x86_64 host.
